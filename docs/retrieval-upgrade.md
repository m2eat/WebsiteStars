# 检索升级与质量验证

## 已实现路径

保留 IndexedDB/Dexie 与 AI SDK Agent。数据库 v3 追加可重建的 `sourceChunks`、`sourceIndexes`、`chunkVectors`，不迁移或覆盖原始收藏字段、笔记与聊天记录。

- 按 Markdown 标题、段落和代码块拆分来源，保留章节与偏移；内容哈希用于增量更新。
- 独立 Embedding 连接，支持 HTTPS 和本机 OpenAI-compatible `/embeddings`；与聊天模型分开配置。
- 开启后只对符合发送规则的来源建向量。私人笔记、独立划词、人工简介/标签覆盖和 AI 生成描述不作为向量来源。
- 关键词分块召回与向量相似度合并，去重到收藏，再选择多个相关章节。向量计算在扩展后台分批执行并让出事件循环，不占用页面主线程；当前为精确向量扫描，不是近似最近邻索引。
- 语义服务失败或索引缺失时退回关键词检索，并在工具结果返回模式与提示。
- 小资料库先给 Agent 概况；支持分页浏览、来源/语言别名、排除上一轮候选、比较与独立模型重排工具。
- 功能引用只能来自已返回的正文/来源描述；标题只允许用于显式标识收藏，不能当成功能证据。
- 工具为已返回的原文附上证据编号，模型可直接选择编号，由本地取回原文，避免翻译、改写或重新抄写引起引用失败。旧的逐字引用方式仍可用。
- 引用格式或证据选择不合格时，在原查询步数、调用数和超时预算内允许一次纠正；已删除、变更或禁止发送的来源仍立即终止查询。纠正后的最终回答替换未核验草稿，不把两版回答拼接。
- 查询卡片只来自已完成回答的最终有序结果，不合并搜索、读取、重排或纠正阶段的候选。回答选择 2 条时显示 2 条；失败、停止和无匹配不显示候选卡片。运行记录保留候选数量，卡片支持详情和原网页；删除项不保留旧链接，变更后不沿用旧证据。
- 允许用户单独启用本地笔记辅助召回。笔记仅在本地计算相关度，模型只接收允许发送的候选来源。

## 查询卡片与引用纠正验证（早期实现，2026-09-23）

新增用例验证证据编号只能指向本轮已暴露的原文、跨收藏或伪造编号被拒绝、标题不能冒充能力依据，以及一次纠正后仍无效时停止。完整自动化套件 408 项通过，类型检查通过。

5 个浏览器流程覆盖聊天与侧栏、失败和停止时保留卡片、重试、自动纠正后替换草稿、详情和原网页打开、删除后刷新、Markdown 流式、语义降级及明暗响应式；最终打包后重新执行新增卡片流程通过。

本机 `qwen3:4b` 单条英文资料的中文模糊查询通过。另用 3 条合成 UI 简介验证逐条比较，最终三条均返回有效原文引用，耗时约 131 秒。首次比较在 120 秒单请求限制下超时；调整小库策略以避免简单比较中的重复读取/重排，并使用产品默认 180 秒单请求限制后通过。两项同时改变，不能据此独立归因或宣称模型响应速度已提升。这些样本不含个人收藏，不代表所有真实问题都能正确推荐。

## 最终结果与搜索工作流修订

先前把检索候选合入结果卡片，导致回答推荐两条而界面显示十二条。已移除该合并：卡片仅由成功提交并持久化的最终引用列表生成，顺序和数量一致。旧会话也遵循该规则，无需迁移收藏。

系统提示词独立在 `lib/query-instructions.ts`，按理解需求、召回、核对、筛选、提交组织。候选仅表示可能相关；默认剔除弱相关资料，部分符合要说明限制，允许零结果和澄清问题。模型应使正文推荐与最终清单逐项一致；相关性判断仍依赖模型，原文匹配校验不能证明每一句总结都成立。

工具新增批量读取，复用相同搜索与片段调用；最后两步预留提交与一次纠正。条件型追问带入原始主题，明确的语言、来源和排除条件在最终提交重新检查。历史序号基于先前最终结果，删除后保留空位，避免“排除第二条”错指其他收藏。

验证：全量 416 项自动化测试通过，随后新增的空结果追问用例与相关模块共 98 项回归通过，TypeScript 检查通过。5 个浏览器流程覆盖真实扩展；最终卡片流程在打包后重新运行通过。该流程明确让搜索返回 12 条、模型提交第 11 和第 2 条，验证只显示这两张卡片且顺序正确，并覆盖零结果、失败、停止、一次纠正、旧会话、来源变更、删除、原网页打开及两种页面的桌面/窄屏明暗主题。

真实本机 `qwen3:4b` 在 12 条合成来源（包括其他平台机器人和通用聊天 UI 干扰项）中仅选择 2 条微信相关来源，并指出辅助回复需要手动发送、协议接口不是现成自动回复机器人。路径为小库概况 → 一次引用纠正 → 最终提交，耗时约 278 秒。测试未读取个人收藏，向量未启用；它验证这个样本的最终筛选，不能证明所有真实查询的准确率，也不能证明响应速度提升。

框架阶段控制依据：[AI SDK Loop Control](https://ai-sdk.dev/docs/agents/loop-control)。

## 配置与索引

在「设置与数据 → 语义检索与索引」填写 Embedding 服务地址、模型及所需密钥，阅读发送范围说明后开启并保存。对于已运行的本地 Ollama，可填写 `http://127.0.0.1:11434/v1` 和已安装的多语言模型，例如 `bge-m3:latest`。扩展不安装服务、不下载模型；浏览器内置推理模型属于后续可替换的接入方式。

开启语义后，现有和新增/导入收藏的允许来源参与自动建索引；关闭时仍可用关键词和分块查询。失败状态不会伪装为就绪，重建只清理派生数据，不删除原收藏。更换向量模型或端点后重建相应向量，旧模型向量不能与新查询向量混用。更换Key不应强制重新计算已就绪的相同模型向量。

普通资料库输入框仍提供即时关键词搜索；Agent 使用混合检索并可主动进行多轮查找。搜索质量取决于来源完整度、向量模型及 Agent 策略，索引状态区用于区分“未采集正文”和“检索无匹配”。

实际实现评测命令：

```sh
STARTS_LIVE_EMBEDDINGS=1 npx vitest run tests/retrieval-live.test.ts
```

该命令只连接明确的本机地址，普通 `npm test` 默认跳过它。评测会在 fake-indexeddb 内保存合成资料、建立真实向量、调用项目的 `LocalRetrievalService`，不读取真实扩展数据库。

这是一组很小的跨语言冒烟评测，不是代表真实用户语料的盲测。其关键词基线不包含旧 Agent 的语言改写，因此不等同于“旧版 Agent 命中率为零”。不能据此保证所有查询都提升。后续应扩充相近项目、错误记忆、多条件否定、真实长文与无答案问题，单独统计召回、误推荐、证据支持程度、延迟和模型费用。
